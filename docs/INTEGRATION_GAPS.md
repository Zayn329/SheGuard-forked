# SheGuard Integration Gaps & Architecture Analysis Report

This document presents a comprehensive evaluation of all major and minor integration gaps identified across the SheGuard application harness (Android client, background services, local Room persistence, mesh transport, and FastAPI backend).

---

## Executive Summary

SheGuard implements an **offline-first intelligent safety system** adhering to the canonical pipeline:
`Report → Local Persistence → Detect → Trust → Alert → Mesh Propagation → Optional Backend Sync`.

While the core 5-phase SheGuard deterministic pipeline is implemented and verified with high unit-test coverage (221 passing unit tests), a detailed integration audit reveals several **Major** and **Minor** integration gaps between application layers, navigation flows, background services, and backend synchronization handlers.

---

## 1. Major Integration Gaps (Critical User Flow & Architectural Gaps)

### Major Gap 1: Disconnected System Notification Intent Deep-Linking
- **Component(s):** `MainActivity.kt`, `SheGuardMeshAdapter.kt`, `SafetyForegroundService.kt`
- **Description:** `MainActivity.kt` contains `showIncomingMeshNotification()` which sets an intent extra `TARGET_SCREEN` (e.g. `SHEGUARD_REPORTING` or `TRUSTED_ALERT`) on system notification pending intents. However, `MainActivity.kt` never reads `intent.getStringExtra("TARGET_SCREEN")` in `onCreate()` or `onNewIntent()`.
- **Impact:** Tapping a system notification (e.g. "🚨 Early Warning Alert Received via Mesh") launches the app onto the default `HOME` screen instead of taking the user directly to the alert details or SheGuard reporting screen.
- **Severity:** High (UX / Critical Emergency Flow)

### Major Gap 2: Dashboard Early-Warning Alert Visibility Disconnect
- **Component(s):** `HomeDashboardScreen` (`SaharaScreens.kt`), `AlertRepositoryImpl`, `RisingPatternAlertEngine`
- **Description:** `HomeDashboardScreen` serves as the primary SheGuard Command Center. However, active rising-pattern early warnings generated by `RisingPatternAlertEngine` or received via mesh were only rendered inside `SheGuardReportingScreen`. A user on the main dashboard had no immediate visual indication when an early-warning risk pattern was active in their proximity.
- **Impact:** Critical early warnings are hidden until the user explicitly navigates into the nested SheGuard Reporting sub-screen.
- **Severity:** High (Preventive Safety UX)

### Major Gap 3: Missing Automatic Micro-Report Sync Handler
- **Component(s):** `MicroReportRepositoryImpl`, `SheGuardSyncManager` / `WorkManager`, FastAPI `/api/v1/sync/batch`
- **Description:** `MicroReport` domain models support `SyncStatus` (`LOCAL`, `MESH_QUEUED`, `SYNCED`). The FastAPI backend exposes `/api/v1/sync/batch` which accepts sync events. However, no background Android `Worker` or `SyncManager` queries unsynced micro-reports from `MicroReportRepository` upon network reconnection to execute batch sync.
- **Impact:** Micro-reports remain permanently in `SyncStatus.LOCAL` or `SyncStatus.MESH_QUEUED` on the Android device, preventing optional cloud-level risk aggregation when online.
- **Severity:** High (Backend Integration & Multi-Device Sync)

## 2. Minor Integration Gaps (UX Polish & Secondary Workflow Gaps)

### Minor Gap 1: Unlinked Manual Panic Trigger to Micro-Report Pipeline
- **Component(s):** `PanicController.kt`, `IncidentStateMachine.kt`, `MicroReportRepositoryImpl`
- **Description:** When a user triggers manual emergency panic via `PanicController` or in-app emergency buttons, an `Incident` is activated and pre-roll evidence is captured. However, manual panic activations do not automatically seed a corresponding local `MicroReport` entity into Room DB (unlike background sensor distress signals in `SafetyForegroundService`).
- **Impact:** Manual distress calls do not contribute to local spatio-temporal pattern clustering or mesh early warnings.
- **Severity:** Medium

### Minor Gap 2: Unused UI Action Callbacks & Screen Parameters
- **Component(s):** `SaharaComponents.kt`, `SaharaScreens.kt`
- **Description:** Several Jetpack Compose components contain unused parameters or empty callbacks (e.g., `statusText` in `BreathingSafetyVisual`, `onShareCircle` in `NotifyCircleManagementScreen`, `onCall` / `onGetDirections` in `TrustedContactAlertScreen`).
- **Impact:** Minor code cleanliness and visual state feedback gaps during UI interactions.
- **Severity:** Low

### Minor Gap 3: Foreground Service Lifecycle and Mesh Adapter Initialization
- **Component(s):** `SafetyForegroundService.kt`, `MainActivity.kt`
- **Description:** `SafetyForegroundService` creates its own standalone fallback instances of `NotifyCircleManager` and `NearbyConnectionsMeshRelay` if unbound from `MainActivity`. However, it does not share the live `SheGuardMeshAdapter` initialized in `MainActivity`, creating a potential state duality for mesh alerts generated while in background.
- **Impact:** Background mesh alert broadcasts could use uncoordinated transport state.
- **Severity:** Medium

---

## Remediation Plan & Recommendations

1. **Fix Intent Deep-Linking (`MainActivity.kt`):**
   Read `TARGET_SCREEN` in `onCreate` and `onNewIntent` to set `currentScreen` state dynamically upon notification tap.
2. **Elevate Alert Visibility (`HomeDashboardScreen`):**
   Collect active `RisingPatternAlert` items from `AlertRepository` on `HomeDashboardScreen` and display a prominent warning banner when risk patterns are emerging.
3. **Bridge Background & Foreground Mesh State:**
   Ensure `SafetyForegroundService` binds directly to `SheGuardMeshAdapter` from `MainActivity`.
4. **Implement MicroReport Sync Worker:**
   Add a WorkManager job to synchronize `SyncStatus.LOCAL` micro-reports to `/api/v1/sync/batch` when network connection is restored.
